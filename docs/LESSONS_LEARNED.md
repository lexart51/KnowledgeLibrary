# Lessons Learned

## Project Evolution

KnowledgeLibrary evolved from Video Knowledge Manager and earlier video/resource-note workflows into a broader Obsidian knowledge system. The compatibility layer and migration tools remain important because older Video Knowledge Manager notes and legacy Knowledge Library notes still carry useful production data.

## Source And Vault Separation

The plugin source repository at `D:\Dropbox\KnowledgeLibrary` must stay separate from vault data. Source code, tests, docs, and Git history belong in the repository. Daily-use notes and plugin state belong in the active Obsidian vault installation.

## Multi-Vault Connector Architecture

The 6.3 architecture was the right boundary: resource, conversation, and document vaults remain independent, and the plugin reads external vault metadata through connectors. The unified index gives one logical search surface without physically merging vaults.

## Deployment State Loss

Early deployment replaced the installed plugin folder and caused `data.json` loss. The corrected deployment model updates only build artifacts: `main.js`, `manifest.json`, and `styles.css`. State files must be preserved across every deployment.

## Version Synchronization

A release can appear successful while Obsidian still reports an old version if package metadata, manifest, compiled bundle constants, status labels, deployment reports, and persisted `versionLabel` disagree. Release-version synchronization checks became mandatory after the 6.4.1 audit.

## Stable Baseline Value

`6.4.1 LTS` is valuable because it stabilizes deployment, state preservation, diagnostics, backup/restore, and release integrity on top of the 6.4 Universal Search and 6.3 connector architecture.

## 6.5 UX Findings

The 6.5 alpha line exposed real UX risks:

- Home duplicate-resource issues appeared when active-vault items and YouTubes connector entries represented the same YouTube resource.
- Continue Learning became noisy when it treated every unfinished item as active learning.
- Topic Page command paths could silently fail, producing no useful modal, view, or Notice.
- Modal-only navigation was not robust enough for primary workflows.
- Alpha.6 persistent navigation shell work was blamed for a runtime interface lock after navigation between major views. Isolated diagnostic testing (see below) found no genuine unresponsive lock; the likely real cause was a navigation-bar text-rendering defect that made the interface look frozen without actually being frozen.
- The confirmed alpha.6 defect is narrower and precise: on the Library and Dashboard views only, the shared navigation bar's button labels disappear (buttons stay outlined and fully clickable) until a different view is opened, at which point rendering corrects itself immediately. Home, Search, Topics, Collections, and Settings are unaffected. See below for the identified cause and candidate fix.

## Alpha.6 Isolated Diagnostic (August 2026)

Alpha.6 (`v6.5.0-alpha.6-experimental`, commit `8d5fd36`) was deployed under a distinct plugin id into an isolated, non-production test vault (empty vault, no connectors enabled, separate from the 6.4.1 baseline install) specifically to investigate the documented interface-lock defect without risk to production. Findings:

- Static review of `NavigationShell.ts` and the views that call it found no global `document`/`window` event listeners, no `pointer-events` or focus-trap CSS, and a correct `existingLeaf ?? getLeaf(true)` reuse pattern for navigation. None of the usual suspects for a full interface lock were present in the code.
- Manual navigation through Home, Search, Library, Topics, Collections, Dashboard, and the Add Resource modal, including rapid repeated clicks, did not reproduce a genuine unresponsive lock. The interface remained clickable and tab switching worked at all times.
- A precise, confirmed defect was reproduced instead: on the Library and Dashboard views specifically, the shared navigation bar's button labels render invisible while the buttons remain fully clickable in place. Opening any other view (Home, Search, Topics, Collections, Settings) immediately restores correct rendering, including for the nav bar left behind on the Library/Dashboard leaf.
- The defect correlates exactly with one CSS difference. Library's container (`.knowledge-library-view`) and Dashboard's container (`.knowledge-library-dashboard`) both rely on `overflow: visible` (no explicit scroll region of their own). Home's container (`.knowledge-library-home-view`) and Topics's container (`.knowledge-library-topics-view`) both declare `overflow-y: auto; overflow-x: hidden`. The two views without their own scroll region are exactly the two that break; the two that declare one work correctly. This is consistent with a `position: sticky` containing-block/paint bug in the shared nav bar (`styles.css`, `.knowledge-library-shell-nav`, `position: sticky; top: 0`) when it resolves its scrolling ancestor through an outer Obsidian container instead of a view-owned one.
- A candidate fix for Dashboard was built and live-tested, and it did not work. Dashboard's container (`.knowledge-library-dashboard`) had no competing design constraint, so `overflow-y: auto; overflow-x: hidden; height: 100%; min-height: 0;` was added to it directly, isolated into its own rule so it would not leak onto the unrelated selectors it originally shared a declaration block with (`.knowledge-library-progress-field`, `.knowledge-library-editor-form`, `.knowledge-library-relationships-section`, `.knowledge-library-management-list`). It passed all 168 existing tests and was deployed to the isolated alpha.6 test vault. Live testing after a full Obsidian restart (ruling out stale-leaf state) confirmed Dashboard's nav bar labels are still invisible with this change in place. The `overflow` correlation, while real, is not the actual root cause for Dashboard, or is not sufficient on its own.
- Library's nav bar labels were observed rendering correctly in the same live test, without any change to Library's own CSS (`.knowledge-library-view` was deliberately left untouched, for the reason below). This was not caused by anything done here and is not understood; it may be an incidental effect of Obsidian reloading the whole stylesheet after the file changed, independent of which specific rule changed, but that is a guess, not a verified explanation.
- Library's container also cannot safely use the same fix that was tried for Dashboard, independent of the above. It intentionally uses `overflow: visible` so a separate dedicated child, `.knowledge-library-scroll`, handles scrolling for the card grid alone while the header/toolbar stay fixed — a real, already-tested design (`tests/library-view.test.ts` asserts `overflow: visible` on this selector). The nav bar renders as a sibling of `.knowledge-library-scroll`, not inside it, so it ends up sticky relative to Obsidian's outer container rather than the vault's own scroll region. Fixing Library correctly, if its improved behavior does not hold up, means moving the nav bar's render call inside `.knowledge-library-scroll`, which is real implementation work, not a CSS-only patch.
- This diagnostic effort is being closed here rather than continued with further speculative CSS changes. Remote, screenshot-relayed debugging (no direct DevTools access, no way to inspect computed styles or live-edit and observe in real time) has reached its practical limit for this specific bug. Whoever picks this up next should work directly at the machine with DevTools open, not repeat this remote process.
- Neither finding affects the 6.4.1 LTS baseline, which was verified clean in the same isolated-vault methodology before alpha.6 was tested.

## Alpha.6 Nav Bar Fix Confirmed (August 2026)

The candidate fix that resolved the Library/Dashboard nav-bar label defect was `flex-shrink: 0; min-height: 40px;` added to `.knowledge-library-shell-nav` in `src/styles.css`. It was verified live in the isolated alpha.6 test vault at increasing scale using synthetic `KnowledgeResource` data:

- n=50: nav bar labels render correctly on Library, Dashboard, and Home; no genuine interface lock reproduced.
- n=500 and n=5000: fix continues to hold. Dashboard was checked directly at 5000 synthetic items after a full Obsidian restart and renders nav bar labels correctly.
- Two minor cosmetic observations at 5000 items, both reviewed and accepted as non-blocking for personal use rather than treated as defects: the sticky nav bar can be scrolled under by fast-moving page content, and at reduced window widths the dimmed secondary text on dashboard cards visually overlaps the bold primary text. Neither affects functionality or clickability. Revisit only if they become a problem in real production use.

This closes the open item from the isolated diagnostic above regarding volume behavior of the label fix. The original, broader "interface lock" report from the historical production rollback has still not been deliberately reproduced under sustained real-data navigation and remains a separate, still-open question — the fix here addresses the confirmed label-rendering defect, not necessarily whatever originally triggered the production rollback report.

## Add To Library Added (August 2026)

External connector entries (conversations from `Obsidian_Vault`, documents from `_Docs`) were browse/search/open-only, with no favorite, progress, or collection tracking — that functionality only exists on resources that live as real notes in the active vault (`YouTubes`), by the same "external vaults stay read-only" principle that governs everything else about connectors.

`AddResourceService.promoteExternalEntry(entry)` was added to close that gap: it takes a `UnifiedIndexEntry`, checks for an existing resource with a matching `url` (the entry's `open_uri`, an `obsidian://open?vault=...&file=...` deep link back to the original note — never a copy), and if none exists, builds a real tracked resource via the same `createBaseResource` factory every other provider uses, then saves it through the normal repository. Connector `resource_type` values that aren't valid `KnowledgeResourceType`s (`"conversation"`, `"moc"`) map to `"markdown"`; everything else maps through directly or falls back to `"other"`.

Surfaced as an "Add to Library" button on external cards in both Library (Conversations/Documents tabs) and Universal Search results. Verified: 4 new tests (promotion, type mapping, duplicate detection, origin guard) plus the full suite (119/119), clean `tsc --noEmit`, byte-identical builds across sandbox and the real machine, then live-tested in the isolated `KL-6.4.1-Test` vault with the connectors pointed at the real `Obsidian_Vault`/`_Docs` paths (read-only scan, zero risk) before being written to production and deployed as part of `6.4.2` (commit `caf7b21`).

## Cross-Vault Access Model Clarified (August 2026)

The user asked directly whether running the plugin only in `YouTubes` "loses" the idea of universal knowledge across videos, books, and chats. It doesn't — tags already flow through connector scans (`VaultConnectorProviders.ts` reads each external note's own frontmatter `tags:` field into the unified index), so tagging consistently across all three vaults and searching `tag:project-x` from Universal Search in `YouTubes` already produces a unified, cross-source result set. Collections do not currently flow the same way — connector entries only inherit a connector's configured default collections, not their own per-item frontmatter — so collections work reliably only for items already in `YouTubes` (native or promoted via Add to Library). This is a real, documented gap, not a regression; recorded here rather than assumed obvious.

Separately, a real (not hypothetical) three-way install was set up and tested: `knowledge-library-v6-obsidianvault-test`, a distinct plugin id installed directly in `Obsidian_Vault` with its own connectors pointing back at `YouTubes` and `_Docs`. It worked — full local features, its own index, its own resource folder. The trade-off observed firsthand: three independent "active vault" data stores with no reconciliation between them, so the same item can end up tracked differently (favorite/progress/collection) depending on which vault's instance touched it last. Given that trade-off, the decision was to keep `YouTubes` as the one hub, and the test install was removed after being evaluated (its plugin folder deleted from `Obsidian_Vault`, and its entry removed from that vault's `community-plugins.json`). It is not part of the recommended setup and does not need to be recreated unless the three-way model is deliberately revisited.

## Obsidian_Vault Renamed To AI_Chats (August 2026)

The user asked to rename how `Obsidian_Vault` was labeled, and was offered a choice: a zero-risk change to just the connector's display name in the plugin, versus a real vault rename with real breakage risk (folder path, `vaultName`, and every existing `obsidian://` deep link all encode the old name). The safe option was chosen and applied first (`displayName` only, in the production `data.json`'s `vaultConnectors` entry and its cached `connector_statuses` snapshot).

The user then separately used Obsidian's own native "rename vault" feature (via the vault's context menu) on top of that. That feature does not just change a display label — it renames the actual folder on disk. `D:\Dropbox\Obsidian_Vault` became `D:\Dropbox\AI_Chats`, confirmed via Obsidian's own `obsidian.json` vault registry. This is exactly the risk flagged as the non-recommended option, materializing anyway after the fact.

Real breakage this caused, found and fixed directly in production `data.json`:

- The `conversation-archive` connector's `windowsPath` (`D:/Dropbox/Obsidian_Vault`) no longer existed — the connector would have started failing on its next scan.
- Its `vaultName` (`Obsidian_Vault`) no longer matched Obsidian's actual registered vault, which is now named `AI_Chats` (Obsidian derives the vault name from the folder name when no separate override is set).
- All 1,180 already-indexed conversation entries carried a stored `open_uri` of the form `obsidian://open?vault=Obsidian_Vault&file=...` — every one of them would have failed to open, since no vault named `Obsidian_Vault` exists anymore.

Fixed by a scoped find-and-replace directly on `windowsPath`, `vaultName` (2 and 3 occurrences respectively, across the connector config and its cached status), and all 1,180 `obsidian://open?vault=Obsidian_Vault` URIs, verified as valid JSON afterward. Checked separately for any promoted "Add to Library" resource notes with the same stale vault reference in their own frontmatter — none existed yet in production, so no additional files needed fixing. All current-state documentation (`CLAUDE_PROJECT_BRIEF.md`, `README.md`, `ROADMAP.md`, `docs/ARCHITECTURE.md`, `docs/MULTI_VAULT.md`, `docs/PROJECT_STATUS.md`, `docs/QUERY_SYNTAX.md`) updated to say `AI_Chats` and `D:\Dropbox\AI_Chats` throughout; historical narrative entries elsewhere in this file that describe events which genuinely happened under the old name were left as `Obsidian_Vault`, since that was accurate at the time.

Lesson for next time: "just change the label" and "the user might still go rename the real thing anyway" are both real possibilities once a rename is on the table — worth checking the actual current vault registry after any rename conversation, not just trusting the choice that was agreed on.

## Redundant Self-Referencing YouTube Connector Disabled (August 2026)

The user noticed a large batch of noisy, thumbnail-less, badly-titled YouTube cards in Library (auto-generated titles like "Video <id>", status "Pendente") and asked to trace the source. Investigation found a `youtube-resources` connector already present in production before this engagement began, configured with `role: "resources"` pointing at the `YouTubes` vault's own path -- i.e. the active vault re-scanning itself as if it were an external source, with `excludePatterns` completely empty.

Confirmed root cause with an exact count match: `91 - data\backup_pre_v1.0\` (168 `.md` files) plus `91 - data\quarantine_duplicates\` (6 files) = 174, exactly matching the user's reported "videoteca"/"youtube" tag count. That `91 - data` folder is a data-processing staging area (WhatsApp-import reports, tagging reports, JSON indexes) left over from an earlier migration pipeline, not real library content -- its placeholder notes were being indexed as legitimate external resources. Beyond those 174, the same connector likely also re-indexed real active-vault resources a second time as generic external duplicates (no proper YouTube thumbnail fallback, since external entries use a generic file scanner, not the resource-specific enrichment path), explaining a further gap between the 174 tagged files and the larger no-thumbnail count observed in Library.

This connector doesn't fetch any additional YouTube metadata -- connectors are read-only file scanners for *other* vaults, and this one was redundant by construction (`YouTubes` was already the active vault with its own proper resource indexing). Disabled directly in production `data.json` (`enabled: false` on the `youtube-resources` connector, one scoped replace, verified as valid JSON), rather than removed outright, so it stays fully reversible. Confirmed fixed after a full "Reload app without saving" (required -- the running plugin instance holds connector config in memory from load time, so on-disk edits alone do not take effect until reload, `Rebuild unified index` alone is not enough) followed by rebuilding the index: the placeholder cards were gone, filtering Library by Source `youtube` showed only real resources.


## Tag Autocomplete Added To Add Resource (August 2026)

While live-testing "Add Resource" with a real YouTube link, the user wasn't sure whether to type `mikrotik` or `#mikrotik`, and separately asked for the existing tag list to be shown so a new tag can't accidentally duplicate one that already exists under a slightly different spelling.

On the `#` question: `normalizeTag()` in `src/utils/tags.ts` strips any leading `#`, lowercases, and turns whitespace into hyphens before a tag is ever stored, and `TagService.normalizeTags` runs every tag through `TagAliasService.canonicalize` -> `normalizeTag` on save. `#mikrotik` and `mikrotik` are fully equivalent; no functional difference either way.

On the duplicate-avoidance request: `AddResourceService.getExistingCanonicalTags()` already existed (returning every already-normalized tag in the library) but nothing in the UI consumed it. The Collections field in `AddResourceModal.ts` already solved the same kind of problem with a plain HTML `<datalist>` bound to a text input via the `list` attribute -- typing still free-forms a new value, but the browser also offers matching existing values in a dropdown. Added a `renderTagsField()` method that applies the identical pattern to Tags, listing `getExistingCanonicalTags()` as `<option>`s. Deployed to production 6.4.2 (`main.js` verified post-deploy to contain the new `knowledge-library-tag-options` datalist id). Tests: 119/119 passing, `tsc --noEmit` clean.

## Notebook Navigator Thumbnails Traced To A Different Plugin (August 2026)

The user reported a newly added YouTube resource showing no thumbnail in the note-list panel on the left, even though the note's own `thumbnail` frontmatter property held a working `i.ytimg.com` URL. Tracing the rendering code (`KnowledgeLibraryView.ts` `renderMedia`, `thumbnailFallbacks.ts`) showed the thumbnail/fallback URL logic was correct and had nothing to do with the panel in the screenshot -- the panel's layout (date-grouped list, tag pills, excerpt line, thumbnail) matched neither the plugin's Library grid cards nor its Dashboard "Continue Learning" list.

Checked production's `community-plugins.json` directly and found the real answer: the panel is **Notebook Navigator**, a separate community plugin, not KnowledgeLibrary. Its `data.json` had `showFeatureImage: true` and `downloadExternalFeatureImages: true` (so it can show remote thumbnails) but `featureImageProperties: []` -- it was never told which frontmatter property to check, so it only ever found images embedded in older notes' bodies (from a pre-KnowledgeLibrary migration pipeline) and never the `thumbnail` property KnowledgeLibrary writes. Fixed by adding `thumbnail` to Notebook Navigator's own "Feature image properties" setting from Obsidian's Settings UI -- a one-time setting, not a code change, and not something KnowledgeLibrary's repository or deployment has any part in.

Lesson: when a screenshot doesn't match any rendering code in the plugin being worked on, check what other community plugins are installed before assuming it's a bug in this codebase.

## OBSIDIAN Folder Reorganization And _Docs Revert (August 2026)

The user wanted to tidy Dropbox by grouping the three vaults (`YouTubes`, `AI_Chats`, `_Docs`) under one new `D:\Dropbox\OBSIDIAN\` parent folder, ahead of setting up a second machine ("PINHA") as a Dropbox-synced standby. `YouTubes` and `AI_Chats` moved cleanly this way and now live at `D:\Dropbox\OBSIDIAN\YouTubes` and `D:\Dropbox\OBSIDIAN\AI_Chats`. `_Docs` (6,220 items, includes folders shared with other people via Dropbox's own folder sharing) failed with `EPERM` mid-move, both from Obsidian's UI and from a manual Explorer rename -- caused by Obsidian still running in the background (five processes, even with all vault windows closed) holding file handles inside `_Docs`. After confirming Obsidian was fully quit and no data had moved, `robocopy /MOVE` was used instead of a raw `Move-Item`, since Obsidian's own mover and PowerShell's `Move-Item` both do the whole tree as one operation and abort completely on the first locked file (a Dropbox filter-driver hiccup, the same transient-lock pattern seen earlier this session with git objects), where `robocopy` retries per-file and resumes safely. It successfully relocated everything to `D:\Dropbox\OBSIDIAN\_Docs` over several passes, including one file (`_Docs tata\GPS guias e comprovantes\2026-07 GPS KZVM TATA.pdf`) that needed a dedicated final retry.

Once `_Docs` had fully relocated, the user realized this was the wrong call: `_Docs` contains folders actively shared with other people via Dropbox, and moving it via a raw file copy+delete (as `robocopy` does, rather than Dropbox's own rename API) risks Dropbox treating the shared folders as deleted-and-recreated, potentially breaking the share for collaborators -- a real risk that does not apply to `YouTubes` or `AI_Chats`, which are not shared. The user manually copied all real content folders back to the original `D:\Dropbox\_Docs` path themselves, leaving only the `.obsidian` settings folder behind at `D:\Dropbox\OBSIDIAN\_Docs`. That last piece was moved back with a narrowly scoped `robocopy /MOVE` targeting only the `.obsidian` subfolder -- explicitly instructed to touch nothing else under `_Docs` -- restoring `D:\Dropbox\_Docs\.obsidian` intact. Verified via Obsidian's own `obsidian.json` vault registry: the `_Docs` vault entry was never touched by any of this and still correctly points at `D:\Dropbox\_Docs`.

Final state: `YouTubes` and `AI_Chats` live under `OBSIDIAN\`; `_Docs` stays exactly where it always was, at `D:\Dropbox\_Docs`, not grouped with the other two. Answering the user's question directly: an Obsidian vault does not need to be physically nested under a common folder to appear in the vault list -- it is just a name+path entry in `obsidian.json` -- so `_Docs` not being under `OBSIDIAN\` has no functional downside.

Follow-up fix required in KnowledgeLibrary itself: the `conversation-archive` connector's `windowsPath` (`D:/Dropbox/AI_Chats`) no longer existed once `AI_Chats` moved, and the disabled `youtube-resources` connector's `windowsPath` was likewise stale. Fixed with the same scoped-replace-with-backup approach used for the earlier `Obsidian_Vault` rename incident (3 occurrences each of the two stale paths, `_Docs`'s already-correct path left untouched, resulting JSON validated). Since vault names were unchanged by the move, none of the stored `obsidian://` URIs needed fixing this time -- only paths, not names, changed. While auditing this, also found and fixed a real latent bug unrelated to the move: `DEFAULT_VAULT_CONNECTORS` in `src/core/settings.ts` (the fallback config used on a fresh install) still said `Obsidian_Vault` from before that vault was ever renamed to `AI_Chats` -- never caught because production's real `data.json` already had correct values and no test imports the defaults constant. Corrected to `AI_Chats` / `D:/Dropbox/OBSIDIAN/AI_Chats` and the `YouTubes` default path updated to match. `YouTubes_BACKUPS`, a sibling folder to the vault rather than inside it, was deliberately left at its original `D:\Dropbox\Cursos Livros Instrucoes\YouTubes_BACKUPS` location -- Obsidian's "Move vault" only relocates the vault folder itself, not siblings.

## Two Real Parser Bugs Found In ResourceDeserializer (August 2026)

The user reported two freshly-added YouTube resources not appearing near the top of Library's "Sort: added" view, and suspected the Refresh button was broken. Isolated testing (search text found the item under every Type filter, including "youtube") ruled out both the type filter and Refresh -- the item was in the result set the whole time, just not sorted where expected. That pointed at the sort comparator or the underlying data, not the UI.

**Bug 1 -- non-ISO legacy dates sorted incorrectly.** Traced the top-ranked card (an old WhatsApp-migration note with no `created_at` field at all) and found its frontmatter genuinely malformed: `rating: date_shared: "08/07/2025` (a corrupted line merging two fields with a missing closing quote) followed by a second, valid `date_shared: "31/05/2026"` line. `ResourceDeserializer` falls back to `date_shared` when `created_at`/`date_added` are absent, so this legacy note's `createdAt` became the literal string `"31/05/2026"` -- a Brazilian DD/MM/YYYY date, not ISO 8601. `KnowledgeLibraryView`'s "added" sort does plain `localeCompare` on these strings, and `"31/05/2026"` sorts *ahead* of `"2026-08-08T13:39...Z"` purely because `'3' > '2'` as the first character -- a garbage date was winning over genuinely newer, properly-ISO-formatted entries. This is not a one-off; likely many of the ~150 WhatsApp-migrated legacy notes carry this format, meaning "Sort: added" has probably been unreliable for a long time, not just for today's adds. Fixed with a `normalizeDateString()` helper in `ResourceDeserializer.ts` that detects `DD/MM/YYYY` and converts it to proper ISO before it's ever used as `createdAt`/`updatedAt`; also added `date_updated` as a recognized legacy fallback field alongside the existing `date_added`/`date_shared`, since this same note had `date_updated: 2026-07-31` in a field name the deserializer never previously read.

**Bug 2 -- nested metadata objects containing arrays were corrupted on read.** `ResourceSerializer`'s own `serializeValue()` already writes nested objects/arrays as proper multi-line indented YAML (e.g. `metadata:` with `videoId`, a `thumbnailFallbacks:` array, and `provider` as siblings) -- this is the serializer's normal, current output for every YouTube resource, not something only Obsidian's Properties panel produces. But `ResourceDeserializer`'s hand-rolled `parseChildren()` decided list-vs-object by checking whether *any* line anywhere in a block contained a dash, rather than only the lines at that block's own indent level -- so a plain object (`metadata`) that happened to contain one array-valued property (`thumbnailFallbacks`) got misdetected as a flat list, silently discarding `videoId` and `provider` and mangling the URLs into bogus key/value pairs (worsened by a second bug where quoted string list items containing `https:` were themselves misread as embedded `key: value` pairs, purely because of the colon in the scheme). This did not explain the "missing from Library" symptom (title/type/url/thumbnail live outside `metadata` and parsed fine regardless), but it was a real, actively-occurring round-trip corruption bug on ordinary YouTube adds. Rewrote `parseChildren()` to be indentation-aware (only lines at a block's own base indent decide whether it's a list or an object, with true recursion into deeper-indented children) and to never treat a quoted string as a `key: value` pair. Covered both bugs with new regression tests (`tests/storage-view.test.ts`): a metadata-object-containing-an-array round trip, and a `DD/MM/YYYY` normalization check. 121/121 tests passing, `tsc --noEmit` clean.

## Library Refresh Silently Skipped Rendering On Index-Load Failure (August 2026)

The user asked directly whether Library's "Refresh" button actually does anything, since it appeared to have no visible effect. Code review confirmed the button itself is wired correctly (calls `KnowledgeLibraryView.refresh()`, which re-reads resources from disk and re-renders), but found a real ordering flaw: `refresh()` fetched native resources, then loaded the unified index, then called `renderCards()` -- all inside one `try` block. If the unified-index load step threw for any reason, the `catch` showed a `Notice` (easy to miss, auto-dismisses) but `renderCards()` was never reached, so the grid and item count stayed exactly as they were -- indistinguishable from Refresh doing nothing at all, even though the native resource list had, in fact, already been re-fetched into memory. Fixed by splitting the two fetches into separate `try`/`catch` blocks and moving `this.renderCards()` outside both, so the view always re-renders with whatever data successfully loaded, rather than an index-load error silently blocking the whole refresh.

Separately, the user pointed out there was no feedback at all while Refresh ran or after it finished -- no spinner, no success message, nothing to distinguish "still working" from "done" from "did nothing." Added visible feedback: the button now disables and reads "Refreshing..." for the duration of the click-triggered refresh, then restores to "Refresh" and shows a `Notice("Knowledge Library refreshed.")` on completion. `refresh()` gained an `{ announce?: boolean }` option so this Notice only fires for the explicit button click, not for the many internal call sites (`onOpen`, "Add to Library", editing a resource, etc.) that already call `refresh()` silently and would otherwise spam a toast on every unrelated action.

## Delete Button Added To Library Cards (August 2026)

The user asked how to remove a YouTube resource and was told the only way was deleting the underlying note directly in Obsidian -- KnowledgeLibrary had no delete/remove action anywhere in its own UI (confirmed by grepping the codebase; the only "Remove" button that existed was for detaching a relationship link between two resources, not deleting a resource itself). The user then asked for a Delete button on the card, matching the existing Open note / Open resource / Favorite / Complete / Progress row.

Added a "Delete" action to native resource cards in `KnowledgeLibraryView.renderCard()` (external connector cards, which are read-only by design, do not get one). Confirms via `window.confirm()` before doing anything, matching the existing lightweight confirmation pattern already used for connector removal (`VaultConnectorManagementModal`) rather than building a dedicated modal for a single yes/no. Deletes through `app.fileManager.trashFile()` -- the Obsidian API that respects the user's own configured trash preference (system trash vs. Obsidian's `.trash` folder) -- rather than a hard delete, so it is always recoverable the same way any other Obsidian delete would be. Covered with two new tests in `tests/library-view.test.ts`: confirms `trashFile` is called after an accepted confirmation, and that it is never called when the user cancels. 123/123 tests passing, `tsc --noEmit` clean.
